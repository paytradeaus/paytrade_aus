# Email Sending Patterns

Two intentional patterns; pick by use case:

- **DB-template-driven** — `emailTemplateRepo.findOne({ email_type: '<key>' })` → fill placeholders → `emailQueueProducer.emailQueueProducer(...)`. Used for **admin-editable, reusable templates** where the body must be editable from the Communication Management UI without a code deploy: signup/verification/password-reset, notices and `notice-gen-doc`, support replies, contact onboarding, subscription invoices, community digest, generic integration emails. New templates of this kind MUST ship with an idempotent `email_templates` seeder (mirror the `notice-templates-seeder` pattern, key on the unique `email_type` column, do not overwrite existing rows so admin edits are preserved).
- **Inline `header-footer-email` wrapper** — body composed in code, the Handlebars `header-footer-email` template provides the chrome; no `email_templates` row is read or required. Used for **system-generated, event-driven notifications** whose content is fully computed and not meaningfully editable by an admin: admin-composed ad-hoc emails, admin/staff lifecycle (`pt-admin-access`, `pt-admin`), subscription state changes, community moderation, integration status changes (e.g. Xero "connection inactive" notification — `xero-scheduler.service.ts` `notifyPrimaryAdminOfXeroInactive`). New notifications of this kind do NOT need a seeder; they only need the existing `header-footer-email` template (already shipped) and a sensible `EmailTypeEnum` value for the `mail_type` log tag.
