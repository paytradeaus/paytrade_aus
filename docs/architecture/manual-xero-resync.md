# Manual Xero Re-sync by ID (Task #65)

Self-service recovery tool (any company user — STANDARD_USER, ADMIN, PRIMARY_ADMIN — gated by an in-resolver IDOR check that rejects company_id tampering against the JWT). Triggered from a "Manual sync" button next to Refresh in the Sync Log header on the Xero dashboard, opens a `BaseModal` dialog (`ManualXeroSyncDialog`) where the user picks a record type, pastes the Xero ID (or invoice/bill number for invoice_bill), clicks Run sync. Result panel renders inline below the form so the user can run several IDs without closing the dialog. Re-pulls a single Xero record and re-runs the existing inbound webhook handler stamped with `sync_run_type: 'manual'`. New service method `XeroWebhookService.manualXeroResync(decoded, { company_id, type, id })` (~L13262 in `webhook.service.ts`) handles five record types: `invoice_bill` (resolves invoice number → GUID via `getInvoices` with `where: 'InvoiceNumber=="..."'` when input isn't a UUID, then calls `handleInvoiceCreateUpdate`), `payment` (resolves Xero payment → invoice id → `handleInvoiceCreateUpdate`), `bank_transfer` (parses `PT-RET-{id}` reference → linked PT payment → claim invoice → `handleInvoiceCreateUpdate`), `contact` (`handleContactCreateUpdate`), `manual_journal` (`handleManualJournalUpdate`, anti-echo aware via `xeroManualJournalService.findByManualJournalId`). Always writes a template-499 trigger log (`MANUAL_XERO_SYNC_TRIGGERED`) regardless of outcome. Reuses the existing `XeroService.refreshTokenSet` Redis-locked token refresh and the existing `xero` `XeroClient` from the constructor. **Resolver**: `manualXeroResync(company_id, type, id)` mutation in `xero.resolver.ts` gated by `@UseGuards(JwtAuthGuard, RolesGuard) @Roles(Role.ADMIN, Role.PRIMARY_ADMIN)`; non-admin standard users get a guard rejection. Returns standard `StringResponse` with JSON-stringified `{ success, message, syncLogId, resolvedXeroId }` payload, plus the standard `XERO_REFRESH` flow when the refresh token is dead. **Frontend**: `manualXeroResync` helper in `integration.functions.ts` parses the JSON payload and toasts result. New `ManualXeroSyncCard` component appended to `XeroDashboard/index.tsx` (under the cards grid, before Sync Log) — type dropdown + ID input + Run sync button + inline result panel with sync log link. Out of scope (deferred): bulk paste, fuzzy search, bulk re-pull, reverse direction (PT → Xero push), cross-company.

## Task #136 — Two-sided manual sync with payment-status pre-flight

Extends the dialog into a two-sided flow. Same `ManualXeroSyncDialog` component now exposes a second **PayTrade side** picker (search PT claims/payments/contacts by id, reference, contact name or amount) alongside the original Xero-side picker. The user picks any one of: a Xero record, a PayTrade record, or both — then clicks **Check** to fetch a pre-flight summary, ticks **I&apos;ve reviewed this**, and clicks **Run sync**. The dialog routes the sync to the correct direction based on what the user provided and what pre-flight found.

**New service methods on `XeroWebhookService`** (appended after `manualXeroResyncLookup`):
- `manualXeroPaytradeLookup(decoded, { company_id, type, hint })` — read-only PT-side picker. `invoice_bill` searches `PaymentClaims` by id/amount/`claim_reference`/contact name/business name/**project name**/**contract name** (joined via `projectDetails` and `contractDetails`); `payment` searches `PaymentDetails` by id/amount/memo/contact name; `contact` searches `ClientSuppliersDetails` by name/business name. `bank_transfer` and `manual_journal` return an explanatory empty result (PT-side picker not supported — these come from confirming a payment / gross-up journal posting).
- `manualXeroPreflight(decoded, { company_id, type, xero_id?, pt_id? })` — read-only inspection. For `invoice_bill` it live-fetches the Xero invoice (resolving GUID *or* invoice number via `getInvoices` `where: 'InvoiceNumber=="…"'`), runs `XeroWebhookService.classifyRetentionShape(invoice, xeroDetails)` for the `retentionClaimnlineItem` / `codesShared` / `hasBaseLine` / `netRetainedSigned` shape, looks up the local `XeroInvoicesBills` row to detect prior mapping (`pt_claim_id`), pulls the matched `PaymentClaims` row, and surfaces summary lines (contact, totals, amount-paid vs amount-due, retention amounts). It additionally fetches **Xero credit notes for the invoice's contact** via `getCreditNotes` (`Contact.ContactID==Guid("…")`), and builds a **side-by-side payment-leg reconciliation matrix**: PT payments (`PaymentDetails` by `payment_claim_id`, joined to `subPayments` for confirmation status and to `XeroPayments` for prior mapping) are matched against Xero `invoice.payments[]` by amount (±$0.01) and `payment_date` (±2 days). Results land on `xeroSide.legs`, `ptSide.legs`, and `xeroSide.reconciliation = { matched, ptUnmatched, xeroUnmatched, ptUnsyncedConfirmedLegs }`, plus a "Payment legs reconciled" check entry. Returns `recommendedAction` (`import` / `push` / `link` / `blocked`), an `actionSummary` string, an array of typed checks (`{ label, status: ok|warn|fail, detail }`) and a signed `actionToken` (HMAC-SHA256 over `${ts}|${company_id}|${type}|${xero_id}|${pt_id}|${recommendedAction}` keyed by `jwtConstants.secret`, format `${ts}.${action}.${hash}`, 10-minute TTL). For `payment` it live-fetches via `getPayment`, joins `XeroPayments` (`pt_payment_id`) and `PaymentDetails`. For `contact` it joins `XeroContactDetails.pt_contact_id` and `ClientSuppliersDetails`. **Decision table** (both-sides cases): both linked + PT has unsynced confirmed legs → `push`; both linked + amounts agree (Δ<$0.01) → `link` (no overwrite); both linked + amounts disagree → `import` (Xero wins); both unlinked → `link` (re-import binds); only Xero → `import`; only PT → `push`. **Block conditions**: invoice `amountDue ≤ 0.01 AND status === 'PAID'` *and* PT claim `status === 'Paid'` *and* totals disagree by more than $0.01 → `recommendedAction='blocked'` with reason "Both sides are fully paid but their totals disagree." Pushing a `bank_transfer`/`contact`/`manual_journal` from PT is also blocked here (only `invoice_bill` and `payment` have a PT-side push path through this dialog).
- `manualXeroTwoSidedSync(decoded, { company_id, type, xero_id?, pt_id?, action_token, reviewed, preflight_snapshot_json? })` — verifies the action token (must match the canonical tuple, must be ≤ 10 minutes old) **and** verifies the `reviewed` boolean is `true` (server-side enforcement of the "I've reviewed this" gate) before dispatching:
  - `direction='push'` + `invoice_bill` → `XeroInvoicesService.createInvoiceOrBillInXero(decoded, { payment_claim_id })`
  - `direction='push'` + `payment` → `XeroPaymentsService.createPayment(decoded, { payment_id, bank_account_id, retention_account, amount, retention_amount: 0, payment_date, cash_retention, sync_payment: true, sync_transfer: !!cash_retention })`
  - `direction='import'` or `direction='link'` → delegates to the existing `manualXeroResync(...)` (Xero → PT inbound replay). For `link`, the inbound handler attempts to bind the re-pulled Xero record to the chosen PT id by reference/contact during normal mapping.
  - `direction='blocked'` → writes the blocked audit log (template 519) and returns `{ success: false, syncLogId, message: <blockReason> }` without dispatching anything.
- Every code path through `manualXeroTwoSidedSync` writes an enriched sync-log row via `writeTwoSidedTriggerLog` using **template 518 on success / 519 when blocked by pre-flight / 520 when dispatch failed at runtime**. The `api_payload` carries `{ type, xero_id, pt_id, direction, sync_run_type: 'manual', reviewed, outcome, child_sync_log_id, preflight: <snapshot> }`. `important_checks` flattens every pre-flight check (`Pre-flight: <label> = <status> — <detail>`) plus reconciliation counters (matched / PT-only / Xero-only / unsynced-confirmed legs). `history` captures direction, outcome, both ids, the reviewed flag, the action summary, and the linked `child_sync_log_id` (the legacy template-499 row written by the underlying `manualXeroResync` for import/link directions remains in place for backward compatibility).

**New seeded log templates** (`xero-log-templates.json`):
- `518` — succeeded "Two-sided manual Xero sync triggered for {{type}} (direction: {{direction}}). Xero id: {{xero_id}}; PayTrade id: {{pt_id}}." (`error_code: MANUAL_TWO_SIDED_TRIGGERED`, process `Xero > Pay Trade`).
- `519` — failed/blocked "Two-sided manual Xero sync was blocked by pre-flight. Reason: {{block_reason}}." (`error_code: MANUAL_TWO_SIDED_BLOCKED`). Used only when `direction === 'blocked'`.
- `520` — failed at dispatch "Two-sided manual Xero sync failed during dispatch for {{type}} (direction: {{direction}}). Error: {{block_reason}}." (`error_code: MANUAL_TWO_SIDED_DISPATCH_FAILED`). Used when the run was dispatched (push/import/link) but the underlying service reported failure.
- For `push` / `link` / `blocked` directions a legacy template-`499` row is also emitted carrying `enriched_sync_log_id` so consumers that filter by `MANUAL_XERO_SYNC_TRIGGERED` continue to see two-sided runs. The `import` direction does not double-emit (its 499 row is written by the underlying `manualXeroResync`).

**Module wiring**: `XeroWebhookService` constructor injects `@Inject(forwardRef(() => XeroPaymentsService))` for the per-payment push path; `XeroPaymentsService` is added to `XeroWebhookModule.providers`.

**Resolvers** (`xero.resolver.ts`, role guard = STANDARD_USER / ADMIN / PRIMARY_ADMIN with the same in-resolver IDOR check as Task #65):
- `manualXeroPaytradeLookup(company_id, type, hint)` — `Query(() => StringResponse)`.
- `manualXeroPreflight(company_id, type, xero_id?, pt_id?)` — `Query(() => StringResponse)`.
- `manualXeroTwoSidedSync(company_id, type, action_token, xero_id?, pt_id?)` — `Mutation(() => StringResponse)`.

**Frontend** (`integration.functions.ts` + `XeroDashboard/index.tsx`): new helpers `manualXeroPaytradeLookup`, `manualXeroPreflight`, `manualXeroTwoSidedSync` parse the JSON payload. The dialog adds a debounced PT-side picker block (only rendered for `invoice_bill` / `payment` / `contact`), a **Check** button that surfaces the pre-flight panel, and an **I&apos;ve reviewed this** checkbox required to enable **Run sync**. Any change to either picked id resets `preflight` and the reviewed checkbox so the action token can never outlive the inputs it was signed against. The result panel now shows the chosen direction alongside the sync log link.

**Why HMAC the action token** instead of trusting the UI to enforce the gate: the `Run sync` mutation is a public GraphQL endpoint protected only by the role + IDOR guards. An admin user could call it directly without ever opening the dialog, skipping the Check step and therefore the chance to spot a "both fully paid, totals disagree" case. The token binds Run sync to a recent Check call so server-side enforcement is non-negotiable.

### Reuse of the standard inbound flow (import / link directions)

The `import` direction (and the `link` direction, which uses the same code path with the chosen PT id supplied as the binding hint) does **not** ship a parallel "lite" implementation of invoice processing. `manualXeroResync` re-pulls the single record from Xero and then dispatches it back through the production webhook handler — `handleInvoiceCreateUpdate` for `invoice_bill` / `payment` / `bank_transfer` (payments and PT-RET bank transfers are resolved up to their owning invoice and re-played as an invoice update), `handleContactCreateUpdate` for `contact`, and `handleManualJournalUpdate` for `manual_journal`. Each handler is invoked with `sync_run_type: 'manual'` so downstream logging and the anti-echo guard can distinguish it from a webhook delivery, but every other piece of the inbound pipeline runs unchanged: `validateAndProcessWebhookInvoice` (smart contract resolution and smart contract auto-create per the company's Xero integration settings), retention extraction via `classifyRetentionShape` and the retention account-code rules, contact-mapping validation (`XeroContactDetails`), account-code and tax-type validation against the company's chart-of-accounts settings, tracking-category resolution for project / contract, audit-pack PDF caching, and the retention gross-up manual-journal producer. There is no second copy of any of this logic in the manual-sync code path.

### Push direction (PayTrade → Xero)

For `direction='push'` the dispatcher calls the same per-record creators used by the live PayTrade-side workflows: `XeroInvoicesService.createInvoiceOrBillInXero({ payment_claim_id })` for `invoice_bill` and `XeroPaymentsService.createPayment({ payment_id, … })` for `payment`. These are the exact services invoked when a user confirms a payment claim or a payment in PayTrade, so they pick up the company's Xero integration settings (account codes, tax codes, tracking categories), apply the retention recording mode (`ex_gst` / `inc_gst`) with the retention tax-type override, recompute per-line GST as needed, and emit the retention manual journals (Phase 3 gross-up) on the same code path. Smart contract auto-create is not triggered on the push side (it's an inbound-only setting) — the push path assumes the PT claim already references a contract.

### How payment-status is identified and surfaced (full / part / pay less / overpaid)

The pre-flight does this in two layers and surfaces both in the dialog before the user is allowed to tick **I've reviewed this**:

1. **Header classification** — a single typed check (`Payment status: …`) computed from Xero's `amountTotal` / `amountPaid` / `amountDue` / `status`:
   - `paid ≤ $0.01` → **Unpaid** (status `ok`).
   - `paid > total + $0.01` → **Overpaid (credit on file)** (status `warn`) — this is the "pay less / credit note" case where Xero already holds an excess against the invoice.
   - `due ≤ $0.01` or Xero status is `PAID` → **Full payment** (status `ok`).
   - Otherwise → **Part payment / pay less** (status `warn`) — partial payment that isn't a final settlement, with the still-owing amount shown.
   The classification is also stamped onto `xeroSide.paymentStatus` so the response payload carries the label as a first-class field, and the same string is mirrored into the enriched sync-log row's `important_checks` array.

2. **Per-leg reconciliation matrix** — every Xero `invoice.payments[]` leg is matched against every PT `PaymentDetails` row (joined to `subPayments` for confirmation status) by amount (±$0.01) and date (±2 days) and bucketed into `matched` / `ptUnmatched` / `xeroUnmatched`, with a separate counter `ptUnsyncedConfirmedLegs` for PT legs that are confirmed in PayTrade but missing from Xero. The frontend dialog renders this as a side-by-side table with explicit per-row badges (`✓ matched`, `→ push`, `→ import`, `unconfirmed`) so the user can see, leg-by-leg, exactly what each direction will do — full payments line up with one matched row, part-payments show one matched leg plus an unmatched remainder, and pay-less/overpayment scenarios show up as a Xero-only leg larger than the PT total or as a credit note in the contact's credit-note panel (also a typed check).

The recommended-action engine (`recommendedAction = import|push|link|blocked`) consumes both layers: the header status drives the "both sides fully paid but totals disagree → blocked" rule (preventing destructive overwrites of paid records), and `ptUnsyncedConfirmedLegs > 0` flips the action to `push` even when both sides exist, so confirmed PT legs that haven't reached Xero get pushed rather than overwritten by a Xero-side import.

### User guide — how to use the Manual Xero sync dialog

Open from **Xero Dashboard → Sync Log tab → "Manual sync"** (next to *Refresh*). The dialog supports three workflows:

**A. One way: Xero → PayTrade (import)**
Use this when a record exists in Xero but not in PayTrade, or when a PayTrade record is out of date with Xero. Pick the record type, paste the **Xero ID** (or invoice/bill number for invoices/bills) into the Xero-side picker, leave the PayTrade-side picker empty, click **Check**, review the pre-flight panel, tick **I've reviewed this**, click **Run sync**. The system re-pulls the record from Xero and runs it through the same handler as a live Xero webhook — so retentions, smart-contract import, contact mapping, account/tax code validation, tracking categories, and audit-pack PDF caching all run.

**B. Other way: PayTrade → Xero (push)**
Use this when a record exists in PayTrade but not in Xero, or when confirmed PayTrade payment legs haven't reached Xero. Pick the record type, leave the Xero-side picker empty (or paste the Xero ID if you want a both-sides check), use the PayTrade-side search box to find the record by id / amount / reference / contact / project / contract, click **Check**, review the pre-flight, tick **I've reviewed this**, click **Run sync**. The system calls the same `createInvoiceOrBillInXero` / `createPayment` services used by the live PayTrade confirm flows, so retentions, GST recording mode, retention tax-type override, and retention gross-up manual journals are all applied. *Push of a fully-paid Xero invoice from a PT-only claim is blocked at pre-flight* with a remediation hint — paid invoices in Xero must be imported, not overwritten.

**C. Linking 2 existing records**
Use this when both records already exist (in PayTrade and in Xero) but PayTrade isn't aware of the link — e.g. a contact created independently in both systems, or an invoice mapping that was lost. Paste the Xero ID into the Xero-side picker **and** select the matching PayTrade record from the PT-side picker, click **Check**. If the totals agree (Δ < $0.01), the recommended action will be `link` — the system creates the local mapping row by re-fetching the Xero record and binding it to the chosen PT id without re-running the full import (no overwrite of either side's data). If totals disagree, the dialog escalates to an `import` recommendation; if both sides are fully paid and totals disagree, the recommendation is `blocked` and Run sync is disabled with the block reason shown.

**Pre-flight checks that always run** (typed checks shown on the panel before Run sync is enabled):

- *Live Xero lookup* — confirms the Xero record is reachable on the current connection.
- *Mapping* — whether a PT↔Xero link already exists for this record, and to which PT id.
- *Amount agreement* — Xero total vs PT total, with the delta in dollars.
- *Payment status* — Unpaid / Part payment / Full payment / Overpaid (credit on file) — see the classification rules above.
- *Xero credit notes (contact)* — up to 10 outstanding credit notes on the Xero contact, with remaining credit. Helps explain pay-less or overpayment scenarios.
- *Payment legs reconciled* — counts of matched / PT-only / Xero-only legs, and a sub-count of PT-only legs that are confirmed (i.e. should have been pushed).
- *Retention shape* — retention line presence, codes-shared flag, base-line presence, and the signed net-retained amount from `classifyRetentionShape`.
- *Contact / project / contract / bank-account mapping* — for invoice/bill records, validates that the Xero contact / tracking categories / bank account already have local mappings.

**How to find the IDs the dialog asks for**

| Record type | Where in PayTrade | Where in Xero |
|---|---|---|
| **Invoice / Bill** | PT id is the **claim id** — visible at the top of the payment-claim detail page (`/user/payment-claims/<id>`) and as the leading number in any sync-log row's *Reference* column. The PT-side picker also accepts amount, reference, contact name, project name, or contract name. | Either the **Invoice GUID** (Xero URL: `https://go.xero.com/AccountsReceivable/Edit.aspx?InvoiceID=<GUID>`) or the human-readable **Invoice / Bill number** (e.g. `INV-0042`). The dialog accepts either and resolves the number to a GUID via Xero's `InvoiceNumber=="…"` query. |
| **Payment** | PT id is the **payment id** — visible on the Payments page row, on the payment detail page URL (`/user/payments/<id>`), and on its sync-log rows. The PT-side picker also accepts amount, memo, or contact name. | **Payment GUID** — visible in the Xero invoice's *Payments* tab on the payment row (open the payment, the URL is `…/Bank/ViewTransaction.aspx?bankTransactionID=<GUID>`). |
| **Bank transfer (PT-RET retention transfer)** | Not selectable from PT-side — these are produced from confirming a payment with cash retention. Use the *payment* picker instead. | **BankTransfer GUID** from the Xero bank transfer screen, or the `PT-RET-<payment_id>` reference visible in the Xero transaction's *Reference* field. |

After **Run sync**, the result panel shows the chosen direction, the message, and a clickable link to the enriched sync-log row (template 518 succeeded / 519 blocked-by-preflight / 520 dispatch failure) — every two-sided run also writes a legacy template-499 trigger row so existing Sync Log filters by `MANUAL_XERO_SYNC_TRIGGERED` continue to surface it.

## Task #141 — Retention-transfer pre-flight check (gross-amount aware)

For paid-with-retention invoices/bills the pre-flight now adds a typed check that asks Xero whether a corresponding `BankTransfer` (the gross retention move into the trust account) actually exists. The check uses a single source of truth — `XeroWebhookService.computeExpectedGrossRetention(retentionExGst, lineAmountTypes, recordingMode)` — that mirrors the producer rule in `getRetentionLineSpec()`: PT stores `retention_amount` ex-GST, and we gross it up (×1.1) only when the Xero invoice's `lineAmountTypes` is `Inclusive` AND the integration's `retention_recording_mode` is `inc_gst`. For Exclusive invoices, or when recording mode is `ex_gst`, the BankTransfer was pushed at the ex-GST figure so no gross-up is applied. The same helper is reused by the live inbound flow's amount-mismatch diagnostic so the two paths can never drift.

The pre-flight queries `accountingApi.getBankTransfers` and filters client-side to a **±7 day window** around any payment leg's date, with two match strategies (a `PT-RET-{payment_id}` reference round-trip first, then exact-amount within $0.01). The decision tree:

- **Match found** → `Retention transfer present (BankTransfer X, $Y on dd/mm/yyyy)` (status `ok`). Surfaced on `xeroSide.retentionTransfer = { bank_transfer_id, amount, date, matched_by, expected_gross }`.
- **In-window candidate but wrong amount** → `Retention transfer amount mismatch` (status `warn`) with the expected gross vs found amount. Surfaced on `xeroSide.retentionTransferMismatch = { expected_gross, found_bank_transfer_id, found_amount, window_days }`.
- **No candidate** → `Retention transfer leg missing — is_retention_confirmed will remain unticked on PayTrade` (status `warn`). Surfaced on `xeroSide.retentionTransferMissing = { expected_gross, window_days }`.
- **Xero API error** → `Retention transfer check` (status `warn`) with the failure message; non-fatal so the rest of the pre-flight still runs.

The same gross-amount-aware diagnostic is mirrored into `validateAndProcessWebhookInvoice` — when the existing inbound matcher returns zero candidates, we re-scan the same `bankTransferResponse` for an in-window candidate that touches the payment account but mismatches the expected gross, and emit a structured **template 521** (`RETENTION_TRANSFER_AMOUNT_MISMATCH`) sync-log row before the legacy "no retention transfer identified" abort. This is **log-only** — the existing block-and-return-false behaviour is unchanged, and PT-side `is_retention_confirmed` flipping logic, the gate-split confirm UI, and the outbound push paths are all untouched. The diagnostic gives operators a clear "the net was transferred instead of the gross" signal that was previously invisible behind a generic missing-transfer message.

**Out of scope (deliberate)**: auto-creating the missing BankTransfer (push-side concern, not a recovery tool); flipping `is_retention_confirmed` from the pre-flight; changing the gate-split Confirm Retention UI; widening beyond invoice/bill record types in the manual re-sync.
