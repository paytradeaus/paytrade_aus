# Xero Payment/Retention Sync Gate Split (Task #50)

Each confirmation checkbox now fires its own Xero leg independently — Confirm Paid → `Payment` API; Confirm Retention → `BankTransfer` API. Previously both had to be ticked before any push fired. New `xero_payments.bank_transfer_reference` column caches the `PT-RET-{pt_payment_id}` reference stamped on outbound BankTransfers; new unique partial index `uq_xero_payments_bank_transfer_id` (where `bank_transfer_id IS NOT NULL`) hard-guarantees one PT row per Xero BankTransfer. Idempotent `XeroPaymentSplitSchemaSeederModule` adds both in production via `ALTER TABLE IF NOT EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS`.

- **Outbound (`xero-payments.service.ts createPayment`)**: Accepts `sync_payment` and `sync_transfer` flags via `CreatePaymentInput` (defaults true). At call time, looks up any existing `xero_payments` row for `pt_payment_id + integration_id` and computes `skipPayment = !wantPayment || existingXp.payment_id` and `skipTransfer = !wantTransfer || existingXp.bank_transfer_id`. If both skipped, returns the existing row without hitting Xero. Otherwise pushes only the missing leg(s) and **updates** the existing row instead of inserting a duplicate. The BankTransfer is stamped with `reference: 'PT-RET-{pt_payment_id}'` for the inbound matcher's round-trip shortcut. The cached reference is persisted to `bank_transfer_reference`.
- **Resolver gate split (`payments.resolver.ts addDetailsOfAPayment` ~L206 + `editDetailsOfAPayment` ~L840)**: Both call sites now compute `wantPayment = isPaymentChecked && !paymentLegSynced` and `wantTransfer = cash_retention && isRetentionChecked && !transferLegSynced` and fire `createPayment` whenever either is true. The legacy `(isPaymentChecked && isRetentionChecked)` AND-gate is removed.
- **Inbound matcher (`webhook.service.ts` ~L9229)**: Replaces the legacy "OR on accounts + amount" filter with a four-step pipeline:
  1. **Reference round-trip** — prefers transfers whose `reference` equals `PT-RET-{pt_payment_id}` of the existing/previous PT payment (covers webhook echo of an outbound transfer we just pushed). Logged as template **488 — Succeeded**.
  2. **AND on accounts + ±14 day window** — at least one transfer side must equal the payment account AND the *other* side must be a different account; transfer date must fall within ±14 days of the Xero payment date.
  3. **Out-of-window rejection** — same-amount, same-account candidates outside the window are surfaced as template **489 — Failed** (`RETENTION_TRANSFER_OUT_OF_WINDOW`) so users see why nothing matched.
  4. **Multi-match after tightening** — if more than one transfer survives, all candidates are logged as template **490 — Failed** (`RETENTION_TRANSFER_MULTIPLE_MATCH`) and the inbound import returns false. Existing per-row uniqueness check (`checkBankTransferIdExistence`) and the new unique partial index together guarantee a transfer cannot be double-mapped.
- **ACCREC parity (`webhook.service.ts` ~L10895)**: `is_retention_confirmed` no longer requires `invoice.type === ACCPAY`. Inbound ACCREC invoices with cash retention also auto-confirm the retention leg, mirroring the outbound gate split that now pushes BankTransfers for both bills and invoices.
- **Sync log templates 488 / 489 / 490** added at the tail of `xero-log-templates.json` (the `XeroLogTemplatesSeeder` is idempotent — it inserts new ids without overwriting admin edits).
- **Symmetric un-tick → delete in Xero (Task #52)**: Un-ticking a previously-synced confirmation now deletes the matching Xero record so PT and Xero stay in sync. `DeletePaymentInput` carries optional `delete_payment` / `delete_transfer` flags (default true → legacy combined behavior preserved for the existing "Unconfirmed - Unmatched" call site). When either flag is explicitly false, `xero-payments.service.ts` `deletePayment` routes to the new private `deletePaymentPerLeg` helper which fires only the requested leg(s): Payment delete sets `status: DELETED` via `accountingApi.deletePayment` and clears `xero_payments.payment_id` (sync log template **491**); BankTransfer reversal posts a new opposite-direction transfer (retention → operating, swapping `from`/`to`), updates `xero_payments.bank_transfer_id` to the reversal id, clears `bank_transfer_reference` (sync log template **492**). `payments.resolver.ts editDetailsOfAPayment` ~L862 detects the un-tick conditions (`isPaymentChecked === false && paymentLegSynced` and the retention equivalent) and calls `deletePayment` with the matching flags. Per-leg routing in `xero-payments.service.ts deletePayment` triggers whenever either flag is **explicitly provided** (true OR false) so both-leg un-tick (both flags === true) still flows through `deletePaymentPerLeg` and emits the 491/492 sync log entries; the legacy "Unconfirmed - Unmatched" call site omits the flags entirely → both undefined → original combined behaviour. **Per-leg result tracking & partial-failure handling**: `deletePaymentPerLeg` runs each leg inside its own try/catch, accumulates outcomes in `legResults = { paymentRequested, paymentDeleted, transferRequested, transferReversed, errors[] }`, and in dual-leg mode pre-validates the transfer leg's bank-account mappings BEFORE the irreversible `accountingApi.deletePayment` call. If any requested leg failed it throws `new Error(joined)` with `legResults` attached; the resolver catch reads `legResults` and only reverts the un-tick(s) whose Xero side did NOT persist via `paymentsService.revertSubPaymentConfirmation(payment_id, { paid?, retention? })`. This prevents a payment-leg success + transfer-leg failure from re-ticking is_paid_confirmed (the Xero Payment is already deleted) while still re-ticking is_retention_confirmed (the BankTransfer is still live). Inner string throws were converted to `new Error(errMsg)` and the resolver outer catch coerces `error?.message ?? String(error)` so the GraphQL response always carries an actionable string (e.g. "Payment is already reconciled"). **Frontend**: `fetchDetailsOfAPayment` GraphQL data now exposes `xero_payment_synced` / `xero_transfer_synced` booleans (computed via raw SQL against `xero_payments` joined to the active `xero_integration_details` row). `AddPaymentSection.tsx` `onConfirmPaidChange` / `onConfirmRTAPaidChange` show the delete-warning modal only when the checkbox was originally checked **and** the corresponding Xero record is mapped (`patchData?.is_*_confirmed === true && patchData?.xero_*_synced === true`); legacy payments confirmed before Xero was connected un-tick silently. Cancel → checkbox stays ticked.
- **Deferred to follow-up**: reconcile-on-conflict (Xero "exceeds outstanding" recovery), retro re-check scheduler for legacy unmatched payments, refusal-to-untick-once-synced UI guard, moving `retention_details` row creation from "on payment save" to "on confirmation", and the Xero IDs/UI footer tweaks. None of these block the gate-split or matcher tightening landing.
- **Task #141 — Gross-amount-aware retention-transfer presence check**: the manual pre-flight (`manualXeroPreflight`) now surfaces a typed check confirming whether a Xero `BankTransfer` exists for the *gross* retention amount within ±7 days of any payment leg, plus an in-window amount-mismatch warning when a candidate exists with the wrong amount (e.g. net pushed instead of gross). Both the pre-flight check and the matching inbound diagnostic share `XeroWebhookService.computeExpectedGrossRetention()`, which mirrors `getRetentionLineSpec()`'s rule (gross-up only when invoice `lineAmountTypes === Inclusive` AND `retention_recording_mode === 'inc_gst'`). Candidate transfers are **scoped to the mapped retention/trust account** — collected from PT `PaymentDetails.retention_account` and resolved via `XeroBankAccountDetails.pt_bank_account_id` — so unrelated transfers between arbitrary accounts can never produce a false present/mismatch verdict. Amount tolerance is inclusive (`<= $0.01`). The inbound mirror emits **template 521** (`RETENTION_TRANSFER_AMOUNT_MISMATCH`) only when the candidate touches both the payment account AND a mapped trust account, before the legacy "no retention transfer identified" abort — log-only, the existing block-and-return-false flow and `is_retention_confirmed` flipping logic are unchanged. Auto-creating the missing BankTransfer is **explicitly out of scope** (push-side concern, not a recovery tool). See `docs/architecture/manual-xero-resync.md` for the full pre-flight decision tree.
