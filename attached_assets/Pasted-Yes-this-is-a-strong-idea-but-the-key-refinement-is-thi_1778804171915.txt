Yes — this is a strong idea, but the key refinement is this:

**The Pay Trade AI agent must not directly “do things” in the database. It should only act through controlled Pay Trade server-side tools, with permissions, approvals, audit logs, reversible action batches, and clear status tracking.**

OpenAI’s current agent pattern supports this well: the app owns orchestration, tools, approvals and state; function/tool calling lets the model request actions, but your application executes the actual code; guardrails and human review should be used around sensitive side effects; and agent state can be stored/resumed when a run is interrupted or awaiting approval. ([OpenAI Developers][1])

Below is a refined, Replit-ready build spec.

# Pay Trade AI Agent System — Build Specification

## 1. Core product concept

Add a **Replit-style AI messenger agent** into Pay Trade that can:

1. Understand the current page the user is on.
2. Understand the current Pay Trade business/project/trust/compliance status.
3. Create a plan before acting.
4. Break the plan into visible task steps.
5. Use approved Pay Trade toolkits to carry out work.
6. Pause when user input, file upload, approval, or missing data is required.
7. Record every action in an audit trail.
8. Allow AI-created changes to be reverted where technically and legally possible.
9. Self-review its work against the original task.
10. Show cost, duration, token usage, tool calls and step history.

The agent should feel similar to Replit’s assistant: visible plan, visible breadcrumbs, expandable work steps, stop/resume behaviour, file upload prompts, approval prompts, and a clear “what I did” trail.

# 2. Recommended architecture

Use a **Pay Trade Agent Orchestrator** on the backend.

The frontend chat panel should never call OpenAI directly. It should call your own backend:

```txt
Frontend AI Messenger
        ↓
Pay Trade Agent API
        ↓
Agent Orchestrator
        ↓
Tool Registry / Toolkits
        ↓
Pay Trade Database / Xero / Procore / Email / Notices / Files
        ↓
Audit Log + Revert Ledger + Cost Ledger
```

OpenAI should be used for reasoning, planning and tool selection. Pay Trade should remain responsible for permissions, database writes, external API calls, audit logging, and approvals. This matches OpenAI’s tool-calling model, where the model requests a tool call and your application executes the function with controlled inputs and outputs. ([OpenAI Developers][2])

# 9. Tool risk levels and approval rules

Use strict approval levels.

| Risk level  | Example                                       | Approval rule                                                            |
| ----------- | --------------------------------------------- | ------------------------------------------------------------------------ |
| Read        | Check status, list missing contacts           | No approval needed                                                       |
| Draft       | Draft notice, draft contract update           | No approval, but label as draft                                          |
| Write       | Update contact, update contract draft         | Approval required unless user explicitly requested and permission allows |
| External    | Send notice, sync to Xero, email contact      | Always approval required                                                 |
| Financial   | Generate ABA, confirm payment, trust transfer | Always approval required                                                 |
| Destructive | Delete, reverse, archive, overwrite           | Always approval required                                                 |

The agent may prepare work, but should not send notices, confirm payments, sync financial data, finalise reconciliations, delete records, or alter trust-critical data without explicit approval. OpenAI’s agent guardrail guidance specifically recommends human review before sensitive side effects such as edits, cancellations, shell commands or sensitive tool actions. ([OpenAI Developers][4])

# 16. Revert system

Every AI write action should belong to an action batch.

```ts
ai_action_batches {
  id
  run_id
  plan_step_id
  status: "open" | "committed" | "reverted" | "partially_reverted" | "not_revertible"
  created_at
  committed_at
  reverted_at nullable
}
```

Each database write should store:

```ts
ai_action_events {
  id
  batch_id
  entity_type
  entity_id
  operation: "create" | "update" | "delete" | "external_send" | "external_sync"
  before_snapshot jsonb
  after_snapshot jsonb
  revert_strategy
  revert_status
}
```

Revert types:

```txt
create → soft delete or hard delete if safe
update → restore before_snapshot
delete → restore if soft deleted
external send → not truly reversible; create compensating record
payment confirmation → not auto-revert unless business rules allow
Xero sync → create reversal/update task, not silent undo
notice sent → cannot unsend; record correction/voiding action if applicable
```

Important rule:

**The UI must not promise “undo” for actions that cannot legally or technically be undone.**

Use labels:

```txt
Revert available
Partial revert available
Compensating action available
Not reversible
```

# 17. Stop and resume behaviour

When the user presses stop:

1. The frontend sends:

```txt
POST /api/ai/runs/:runId/stop
```

2. Backend cancels or pauses the active model response.
3. Backend stops scheduling new tool calls.
4. Current atomic database transaction is allowed to finish or safely roll back.
5. The run is marked:

```txt
status = "stopped"
```

6. The agent records:

```txt
completed steps
current step
pending steps
last safe checkpoint
part-done warnings
records changed so far
whether resume is possible
```

OpenAI’s Responses API supports background responses, cancellation of in-flight responses, and streaming with a sequence cursor for reconnect/resume-style interfaces; use this pattern for long-running agent work rather than relying on a single fragile request. ([OpenAI Developers][6])

Example stopped message:

```txt
Stopped.

Completed:
✓ Checked compliance status
✓ Found 2 unsent notices
✓ Drafted 1 notice

Not completed:
- Draft second notice
- Request approval
- Send approved notices

Warning:
One draft notice was created but not sent. It is safe and waiting for review.

[Resume] [Discard plan] [Revert AI draft]
```

- ai_action_batches
- ai_action_events
- ai_unresolved_work_items
- ai_usage_events

Create a central tool registry. Every tool must have a name, description, input schema, output schema, risk level, permission requirements, approval requirement, idempotency key and revert strategy.

The agent must create a visible plan before any multi-step task. Each plan step must appear in the AI panel and be expandable to show what the agent did, which tool it used, what records were inspected or changed, duration, cost and approval/revert status.

When a file is required, show an upload component above the message input. When approval is required, show an approval component above the message input. The agent must pause while waiting for uploads or approvals.

The send arrow must become a stop button while the agent is running. If stopped, the backend must stop the run, save completed steps, pending steps, active step, affected records, last safe checkpoint and unresolved work warnings. The user must be able to resume, discard or revert AI-created draft work where possible.

All AI actions must be recorded as the active user delegated to AI, e.g. "Philip Taylor — AI", using actor_user_id plus actor_mode = "ai_delegate". Do not create a fake AI user.

Every AI write must belong to an action batch with before/after snapshots. Revert must be available for safe database actions. External sends, payment confirmations, Xero syncs and notices already sent must not be falsely labelled as reversible; instead show compensating action options.

The agent must self-review every completed run against the original user task and identify completed steps, skipped steps, failed steps, unresolved issues, approvals still pending and whether any revert is available.

Use strict guardrails:
- read-only checks can run without approval
- draft creation can run if the user requested it
- sending notices, confirming payments, finalising reconciliations, syncing to Xero/Procore, deleting records, changing trust-critical data or generating/confirming ABA/payment actions must require explicit approval

The system should use OpenAI through the backend only. The frontend must not expose the OpenAI API key. Use streaming for live progress and support background/resumable runs for longer tasks.
